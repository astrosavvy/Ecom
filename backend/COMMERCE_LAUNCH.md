# Razorpay and Shiprocket launch runbook

Implementation date: 7 October 2026. Checkout is disabled by default. No live charge, refund, courier booking, pickup or customer message is part of development QA.

## Preparation before credentials

1. Open `/admin/launch` as the owner. Confirmed defaults are YOUNOYA HOUSE OF ASTRO PRIVATE LIMITED, support@younoya.com, free India / INR prepaid delivery, dispatch within 24 hours of payment confirmation, and estimated delivery 3–5 working days **after dispatch**. Remote delays are possible.
2. Fill the real public business address, support phone, grievance officer/contact, issue-report window and refund-initiation timeframe. Review all five public policies. Do not publish an incomplete policy or enter invented details. Owner publication retains an immutable settings snapshot and revision; checkout binds that revision to the signed cart and resulting order. Policy document version is 2026-10-07; code revisions remain in Git.
3. Confirm tax registration, applicable HSN and GSTIN if registered. Configure actual Medusa regional tax/pricing rules, seller invoice details in Shiprocket and product disclosures. Do not mark tax/invoice preparation complete based solely on typing a GSTIN. Use the default HSN only for items sharing its verified classification; use per-variant HSN overrides for differing products/hampers. Each accepted order freezes its classifications. The explicit tax/invoice verification gate remains false until these external configuration checks pass. Invoice generation follows the provider/account setup; verify actual invoices during controlled setup.
4. Configure the actual Shiprocket pickup location in its dashboard. Save its **exact** name, address and PIN, select the real Medusa stock location and the storefront sales channel, and verify their addresses match the physical pickup. Inventory must exist there for every offered variant.
5. Measure protected product/hamper weights and each empty outer box. Enter cm/kg, compatible variants, maximum units and maximum packed weight. Compatibility is a physical fit approval, not a guess based on dimensions. The smallest verified compatible box is selected; no suitable configuration blocks checkout before payment.
6. Click **Configure free India delivery**, or run the compiled `configure-checkout` Medusa script. It creates the default shipping profile when needed, India service zone, stock/provider/location links and a zero-price prepaid shipping option. Products/hampers must use this default profile. Verify inventory linkage and sales-channel/public-key alignment. Existing items on other shipping profiles require explicit migration before activation.
7. Owner marks business/policy, physical packing and consumer-obligation review only after completion. Razorpay account approval, automatic capture/webhook preparation, Shiprocket account/wallet/pickup preparation and controlled verification remain separate checks. Homepage defaults to Shop; **Homepage → Restore Coming Soon** preserves the earlier implementation.

## Consumer readiness

- Publicly disclose legal business name, geographic address, customer support and grievance contacts. Acknowledge complaints within 48 hours and redress within one month. Record and provide complaint copies. Transaction emails and order requests include actual identifiers and descriptions.
- Policies allow cancellation before dispatch and owner-reviewed damaged/defective/incorrect-item remedies. Reporting windows do not extinguish statutory rights; late issues are still recorded for review. No change-of-mind policy should restrict statutory defective-item or deficient-service remedies. Owner must approve operational timeframes and escalation procedures.
- Check Legal Metrology/packaged goods declarations, actual seller/product/importer/country-of-origin details, MRP/pricing/tax invoices, materials, safety/usage, applicable warranty/expiry and bundle constituents. These depend on the real products and cannot be invented by code.
- If launching on/after **1 January 2027**, complete applicable amended e-commerce obligations: NCH convergence partnership, complaint copies, truthful search and sponsored disclosures, prior-price records (lowest offered price in the prior 30 days), annual dark-pattern audit and prominent compliance certificate. Inventory versus marketplace obligations must be reviewed against the actual operating model. No fabricated certification or price-history claim is published.
- Review actual astrology/birth-data handling and processors against the Privacy Policy. No password, card details or private provider credentials are stored in the browser. Optional birth information is used for requested guidance; statutory privacy requests use the disclosed support/grievance procedure.

## Final credentials and activation

Use `commerce.env.example` as a names-only guide. Set secrets directly in the existing private backend environment. Never place them in `VITE_*`, browser storage, Git, artifacts, public configuration or logs. Shiprocket needs a **separate API-user email/password**, not a storefront key; the server logs in and refreshes its bearer token before its 10-day expiry. A 401 invalidates the cache for a subsequent request; mutations are not automatically replayed.

1. Obtain approved Razorpay/Shiprocket accounts, templates/pickup/wallet and necessary support/business details first.
2. Keep `COMMERCE_LIVE_ENABLED=false`. Enter backend credentials only after preparation. Restart the service so conditional Razorpay registration is loaded, then rerun delivery provisioning to link the payment provider to India.
3. Configure Razorpay automatic capture and signed webhook `https://api.younoya.com/hooks/younoya-razorpay` for payment.captured / authorized / failed. The previous provider hook URL is also intercepted by the durable handler. Sign with the exact configured webhook secret; do not use the API key secret for webhook HMAC.
4. Perform separately authorized controlled provider verification. Use Razorpay test mode for money flows first; inspect amount, INR, refund idempotency, free shipping, actual stock/promotion/tax totals and invoices. Shiprocket does not have an equivalent assumed sandbox: mock development tests, then authorize a controlled real account check explicitly. Do not book pickup just to verify API connectivity.
5. Mark controlled verification complete only after its evidence is reviewed. Set `COMMERCE_LIVE_ENABLED=true` last and restart. `GET /store/site-config` must return `checkoutEnabled:true`; admin readiness must have no blockers. All public pages must be approved and linked before this step. Turning the flag off prevents new checkout; existing captured payments still require reconciliation and after-sales support.

## Lifecycle and recovery

- Medusa 2 catalogue/cart/order/admin amounts use **rupees** (`inr-major-v2`). Razorpay alone uses integer **paise** at its explicit provider boundary; Shiprocket receives rupees. ₹1,499 in Medusa becomes 149900 paise for Razorpay and ₹1,499 for Shiprocket. Known legacy financial records require `inr-paise-v1`; unclassified records block processing. See [NAVRATRI_RELEASE.md](NAVRATRI_RELEASE.md) for the reviewed migration and rollback. INR orders are bounded to ₹1–₹10,00,000. Server totals, stored provider order/session IDs and provider capture are authoritative. Cart approvals bind their unit version, customer or guest cart identity, fingerprint, immutable policy revision and measured shipping snapshot with an HMAC.
- Verified webhook event hashes, pending operations, shipments and after-sales requests persist in PostgreSQL. Signature failures return 401; unavailable durable storage returns 503 for provider redelivery. Per-cart completion and per-order claims use PostgreSQL advisory locks; nested payment compensation reuses the same lock connection. Browser and webhook completion use the same stable Medusa transaction ID, resuming its persisted workflow instead of starting separate executions. Old processing rows become reconciliation work after five minutes. Pending refunds and tracking are reconciled by the minute job.
- Browser abandonment retains its pending cart/session before opening Razorpay. Returning customers recover the completed Medusa `order_cart` link or reopen the same pending payment. Cancellation/failure preserves the bag and contact data. Do not start a second checkout while a payment is uncertain.
- Shipping is created only for authoritative captured payment. A stable `YN-order_*` merchant order ID is looked up before creation. Unknown create/AWB/pickup/cancel outcomes are reconciled against provider state; no blind replacement booking. Staff see paid orders even if fulfillment fails. Owner selects an available courier and approves pickup. Booking/pickup scheduling is not dispatch; tracking handover updates Medusa shipment and delivery separately.
- Owner approves cancellation/refund; support is read-only. Core direct admin cancellation/refund/fulfillment APIs are guarded to avoid bypass. Pickup processing and cancellation approval are mutually excluded. Refund uses the original stable `X-Refund-Idempotency` key, checks remaining captured amount and records pending/processed/failed status. A lost response reuses the exact key and body. An ambiguous monetary outcome is not a new refund.
- **Operation history** offers provider reconciliation. A rejected request proven to have no effect may be retried with the same persisted operation. Uncertain operations cannot be manually marked successful or replayed from the UI; verify the original merchant order/refund in the provider dashboard and resolve precisely through supervised maintenance. SMTP delivery ambiguity is held for staff review to avoid sending duplicates.
- Customer `/account/orders` and details enforce backend ownership. Order pages show payment/shipment/refund status, tracking, actual items and after-sales requests. Phone-only accounts still provide email during checkout. No account merging is performed.

## Build, tests and deployment

- Run local backend `npm run build` (admin disabled), then PowerShell `$env:TEST_TYPE='unit'; npx jest --no-cache --cacheDirectory ../.tmp/jest-commerce --runInBand --forceExit src/__tests__/commerce*.unit.spec.ts src/__tests__/checkout.unit.spec.ts src/__tests__/otp-*.unit.spec.ts`. Run root `npm run build`.
- `scripts/test-commerce-postgres.cjs` requires `COMMERCE_QA_ISOLATED=1`, a real PostgreSQL connection and built module path. It creates a random `commerce_qa_<hex>` schema, validates migration/concurrency/refund and booking recovery with mocked providers, prohibits unmocked network requests, and drops only its validated schema. Production commerce rows are never used. On VPS use `COMMERCE_QA_RUNTIME` and `COMMERCE_QA_BUILD` for a separate transferred local build, with existing runtime dependencies on NODE_PATH.
- Build **locally only**. Transfer compiled modules/routes/middleware/job/subscriber/config and source/docs over SSH to `/home/ubuntu/younoya/backend`. Preserve `.env*`, dependencies and uploaded media. Back up prior runtime code first; run additive `db:migrate --skip-links`, restart PM2 `younoya-backend`, allow up to 90s for cold health, and verify safe config/auth gates before frontend release. No GitHub is involved in backend deployment.
- Check 360/430px mobile and 1024/1920px desktop, keyboard focus, mobile form scrolling, provider SDK loading/error, and policy links. Mock fixtures must stay out of production/Git. Inspect generated assets and browser requests: no private credentials or direct Shiprocket API calls, only Razorpay's public key ID may reach checkout.
- Real stored autofill, OS keyboard and live provider outcomes require separate device/account verification. Do not claim these based only on viewport simulation. Provider activation remains disabled until owner requirements pass.
